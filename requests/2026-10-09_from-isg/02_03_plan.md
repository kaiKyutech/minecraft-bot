## 3. 02：バグごとの方針

### B1：同じ失敗の反復を有限にする（最優先）

現コードでは、実行失敗または前提不足で再計画するとstepIndexが0へ戻り、同じ失敗に回数制限がない。

- 1回のルートexecuteGoalに属する実行用の失敗記録を設け、道具準備・補助目標・再計画でも共有する。bot間・別のexecuteGoal間では共有しない。
- 同じaction・params、同じ失敗code/理由、同じ関連状態での失敗を **3回（初回を含む）** までとする。3回目で `REPEATED_FAILURE` を返す。
- 関連状態は在庫・装備・GOAP環境facts・ブロック単位の位置・近傍の設置状況などを正規化して比較する。timestamp、時刻の経過、yaw、微小な座標揺れだけでは別状態にしない。実際の材料や設置可能性の変化は区別する。
- 前提不足→補助目標→同じ前提不足の経路も記録し、技能実行のcatchだけに制限を置いて抜け道を残さない。必要なら関連状態で進展のない再計画の合計にも **10回** の安全上限を設け、同じコードで `limitKind` を区別する。
- detailsに goal、action、params、reason/code、attempts、limit、limitKind を入れる。runnerの数量削減等のcatchがこの終了を握りつぶさず、公開Resultまで伝わるようにする。
- 正常な採集の反復、実際に環境が変わった後の再試行、AbortSignalは維持する。再計画後の成功もテストする。

今回は失敗actionを除外する代替計画探索を追加しない。まず有限回の実行再試行で早く失敗を返す要件を満たし、通常の計画結果を維持する。代替探索は任意の追加案として報告に残す。

検証：変わらない状態でplace_furnaceが必ず失敗するofflineテスト、前提不足ループ、補助目標での終了伝播、実際に状態が変わる再試行、中断。地下y=16の幅1通路のライブ試験はB2と合わせ、設置・精錬の成功または有限の失敗を確認する。

## 4. 03：追加APIの契約

すべて既存の `Promise<{ ok, data, error }>` に統一する。候補ごとの不能・未評価は正常な一括評価のdataとして表す。
旧API・チャット入口は維持し、新機能は関数APIへ追加する。

### F1：evaluateGoals（最優先）

提案入口：`api.evaluateGoals(goals, { worldState, maxMs = 1000, signal } = {})`。

dataは `results`（入力順）、`durationMs`、`timedOut`、観測・初期準備・評価の時間情報を持つ。各候補は次の形を基本とする。

```js
{
  goal,
  status: 'plannable' | 'unplannable' | 'unevaluated' | 'invalid',
  plan, stepCount, estimatedMs, estimateDetails,
  resources: [{ block, count, nearestPosition, nearestDistance }],
  diagnosis, reason
}
```

- 同じ完全なworldStateから通常と同じplannerで評価する。planのaction/skill/params/cost・順序を変えない。作れそうな途中経路を完成planとして返さない。
- 全体の単調時刻deadlineを共有する。探索の展開・行動走査・診断にもdeadlineをチェックし、適切にイベントループへyieldする。Promise.raceだけで返して探索を裏で継続する実装にはしない。
- 制限に達した探索中・未開始候補は `unevaluated`、reasonは `budget_exceeded` とする。予算超過を資源不足と断定しない。
- deadline指定は一括評価にだけ適用する。通常planGoal/goap.planのデフォルト探索・診断契約は保持する。
- 同一状態の重複goalの結果は再利用する。cacheは版・goal・計画に必要な状態内容で区別し、入力の変更と状態差を取り逃がさない。入力や返却planが変更されても別評価を汚さない。
- 明白な不能の事前判定は、行動定義から証明できる必要条件に限る。採集可能な設置済みブロック・カテゴリ・道具の自作経路を除外する危険があれば採用せず、deadlineで制限する。
- worldState省略時の完全observe・初回domain準備も時間情報へ含める。予算内に準備できなかった場合は未評価で返す。性能の主測定は起動準備済み＋共有worldStateの毎回の判断用ケースとし、初回・観測込みの所要時間も別に示す。

時間見積もりはA*costとは分離する。gatherの個数・道具・採掘/回収、craft回数、精錬数、移動距離から内訳を作り、02の自然地形試験と追加ライブで係数を実測する。係数・サンプル数・見積もりと実時間の差を記録し、距離は直線距離で地形の到達性を保証しないことをdata/文書に示す。
資源はgatherとmove_to/workbench/smelt等から抽出し、カテゴリを実環境の名前に対応させる。計画が具体座標を指定しないものは最寄りを参考値として扱い、確定した採集先だと表示しない。

検証：70件と同じ状態の計画一致・非破壊性、不能/無効/未評価の区別、重複とcache無効化、deadline停止、中断、実行と並行。自然地形の約20候補（成功・不能を混ぜる）を初回と反復で測り、1秒以内・評価済み件数・未評価件数を併記する。全部未評価で速度だけ達成したとは扱わない。

任意の「作れそうな候補の自動列挙」はF1〜F5の必須部分の後に検討する。今回はまずisgが渡すgoal配列を確実に扱う。

### F3：observeFast

提案入口：`api.observeFast({ range = 16, maxMs = 50, maxChecks, ... } = {})`。

- 位置、度数のyaw/pitch、health/food、time/isDay、inventory/equipment、近隣プレイヤー・落ちたアイテムを軽く取得する。
- 資源は名前/カテゴリごとのcount、nearestPosition、nearestDistanceを返す。範囲は設定可能。全ブロックの大きなlistは返さない。
- まず予算を持つ範囲スキャンと結果再利用を実装する。必要ならbotごとの資源indexを段階的に構築し、blockUpdate・chunk load/unloadで更新する。初回構築・移動・chunk境界・listener解放を検証する。
- 完全に走査できない場合は `complete:false`、observedAt/ageMs、checksUsed、未ロード・打切りを明示する。途中countを正確な全範囲countとして扱わない。位置/在庫は呼出時の新しい値を返す。
- 空の見え方は頭上の読み込み済みブロック/height情報から判定し、上方が未ロードなら `skyVisible:null`。地下/地上はこの観測に基づく推定とする。明るさは足元/目の位置のblock light・sky lightを返し、不明はnull。
- 実行cache、refreshの世代・フラグは変更しない。F1へ軽い観測をそのまま渡す機能は初期範囲に含めず、完全observeの同じworldStateを複数候補へ使い回す。範囲や完全性の違いを無視してGOAP状態に変換しない。

検証：資源要約の数と最寄り、カテゴリ、range、時間予算、未ロード/不完全性、地上/地下、明るさ、移動中の並行取得。フラット/自然の初回・同位置・移動後の反復所要時間を測り、median/p95・完全性・scan範囲を報告する。50ms程度は性能目標であり、完全性を隠すための閾値にはしない。

### F5：moveToward

提案入口：`api.moveToward({ x, z, y? }, { maxMs = 5000, range = 2, signal } = {})`。

- y省略時はGoalNearXZで水平距離を縮める。既存pathfinderの移動能力を使い、歩ける高さへ進む。現在のy固定や未ロード位置の地表高さの推測は行わない。
- y指定時は3DのGoalNearを使う。距離指標はy省略時水平、指定時3Dと明示する。
- 開始/終了position、startDistance/endDistance、distanceReduced、reached、reasonを返す。reasonは `arrived` / `timeout` / `no_path` / `cancelled`。
- 到着・時間切れ・道なしは `ok:true` の結果にし、reachedと距離で部分移動を判別する。部分移動0でもtimeout/no_pathは正常な探索結果として示す。
- 中断だけは既存契約に合わせて `ok:false / CANCELLED`、detailsに同じ移動結果（reason:cancelled）を入れる。入力不正も失敗Result。
- 時間切れ・道なし・中断時に必ずgoalを解除し、発行済み移動の終了と後処理を待つ。maxMsは開始準備待ちを含む全体の予算として扱い、期限後に新しい移動を始めない。終了処理による遅延は実測して示す。

OperationManagerの既存runを使い、GOAP/別移動を置換する。観測・評価は移動中も並行できる。
検証：到着、20〜40ブロック先、障害物で到達不能、未ロードの遠方、y省略/指定、中断、置換、終了後に動き続けないことをofflineとライブで確かめる。

### F4：常設viewer/browser

提案入口：

- `api.startVision({ port, width = 640, height = 360, viewDistance = 4 })`
- `api.captureVision({ type = 'jpeg', quality = 80, ... })`
- `api.stopVision()`

開始時だけviewer＋専用ヘッドレスChromeを起動・初期描画を待つ。startのdataにurl/portと準備時間を返す。captureはすでに描画されたpageを撮り、image（base64）、format、サイズ、position/yaw/pitch/timestamp、durationMsを返す。ディスク保存は任意とし、毎回の撮影に10秒waitやbrowser起動を入れない。

- 同一botのstart/capture/stopと旧visionを逐次化し、stop中の新規撮影、重複起動、起動途中の失敗を処理する。
- 起動・所有・解放の管理をvision内に追加する。既存 `info('vision')` のPNG/1920×1080/保存・描画待ち/方向変更の契約を維持する。一時撮影の後処理で常設セッションを閉じないように資源の所有を区別する。
- stopVisionは冪等。botのend、CLIの正常終了、SIGINT/SIGTERM等の終了経路でもbrowser/viewerを解放する。ライブラリimportだけではGPUを起動せず、ユーザーのChromeやMinecraftクライアントを操作しない。
- botの首を動かさない別方向撮影は、既存viewerのカメラ操作が利用できれば追加する。bot.lookは使わず、撮影中だけカメラを上書きし撮影後に一人称追従へ戻す。安定した仕組みを確認できなければ任意機能として未実装理由を報告する。

検証：連続撮影10枚程度のmedian/p95、0.1〜0.3秒目標、PNG/JPEG・サイズ、移動中、デモ用url、旧visionとの共存、起動失敗/撮影失敗/close失敗の後処理、正常停止・子プロセス終了時にbrowser/viewerが残らないこと。画像を目視確認する。

### F2：executeGoalの進捗

`api.executeGoal(goal, { signal, username, onProgress })` を追加する。既存の完了Resultは維持する。

通知は plan、step_start、step_success、step_failure、replan、subgoal_enter/subgoal_exit、goal_end を基本とする。
各通知にoperationId、sequence、timestamp、goal、depth、planIdを持たせ、stepには0始まりstepIndexとstepCount、action/skill/paramsを付ける。再計画時は新しいplanIdと全planを返し、補助目標には親との関係と成否を含める。

onProgressは実行の観測用とし、戻り値を待ってMinecraft操作を止めない。callbackのthrow/rejectはログへ記録し実行Resultを壊さない。外部でplan/eventが書き換えられても実行内容へ影響しないようにする。旧実行からの通知はoperationIdで識別でき、終了後には通知を残さない。

検証：通常成功、step失敗→再計画、補助目標の入出、道具準備、B1打切り、中断・置換、callback異常、sequence、2bot独立。ライブでも実際のstepと通知を対応させる。

## 5. 同時実行と資源の扱い

| 呼出 | 実行・移動・followへの作用 | 資源・停止 |
